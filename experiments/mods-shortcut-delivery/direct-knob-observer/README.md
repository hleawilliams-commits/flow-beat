# Waveform knob entry observer — unpublished experiment

This unpublished probe was intended to observe the exact-firmware Waveform handler identified in [the static boundary review](../direct-knob-boundary/). Its localhost-emulator function-entry hook was refused, initialization returned `-20`, and no native knob observations were collected. [The failed attempt](runtime-evidence.md) records the refusal and a harness readiness error. Later selective cleanup is verified against a fresh baseline, preserving subsequent legitimate development. It has not been installed on the physical deck.

The probe source does not open a menu, consume or inject input, call a navigation function, or modify either core. Its host and assembly results below describe the observer implementation and forwarding fixture; they do not establish a working native hook.

The handler at `0x1b3ab60` has four live integer arguments; its return class remains opaque. [The AArch64 entry wrapper](abi/entry.S) saves incoming argument registers, vector arguments, the indirect-return register, LR, stack position and status state, calls a nonthrowing scalar-copy helper, restores the state and tail-branches to the original. Native return values and exceptions go directly to the native caller. The original target pointer is loaded with acquire ordering. `x16` is ABI-permitted transfer scratch; the core's island also uses `x17`. This is not a promise to preserve non-ABI uses of those registers.

Only the process main thread can write the fixed SPSC record queue. Unexpected thread entry disables observation; native forwarding continues. Records contain opaque `x0`, `x1`, `w2`, `w3` and caller values. The observer never dereferences a native argument and never reads a native object after a call. The logging worker drains at 500 ms intervals, stops at 128 records, and suspends observation after five unchanged tick samples. This heartbeat is a diagnostic lifecycle limit, not a menu cancellation or input-ownership contract.

Initialization requires exact opt-in `AZ_WAVEFORM_KNOB_OBSERVER_EMULATOR=1`, the exact SDK firmware tag, size-gated SDK services, matching immutable entry instructions and vtable slot, a worker, and an accepted exclusive hook claim. The pinned installer calls `azm_patch_ok(func, 1)` before looking for a branch island. That predicate scans **all four initial instructions** for disallowed PC-relative instructions regardless of patch width. The `TBZ` at entry +8 therefore declines this function even though an accepted island path would copy only the first instruction. The previous eligibility analysis missed that unconditional scan. The corrected verifier executes the extracted predicate and confirms refusal. A failed claim does not retry, replace another hook or weaken any watchdog.

## Verification

- [Installation-boundary verification](install-boundary-result.json) binds the immutable firmware/table to pinned core source and confirms `AZM_DECLINED` before island lookup or code writes. Eighteen host assertions execute the three extracted instruction-policy functions, including one-word/four-word refusal, every initial branch position, and a fixture-only NOP control. They do not execute firmware instructions.
- Eleven additional host assertions execute the extracted SDK vslot segment validator with program-header fixtures from the same ELF. They confirm rejection of this slot's executable segment, valid non-executable bounds, exclusion of other libraries, and acceptance only when a fixture removes the executable flag. No firmware or runtime protection is changed by that control. An independent root rerun reproduced all 29 policy assertions and identical JSON metadata.
- [Host results](host-results.txt): 12,314 assertions per plain, ASan/UBSan and TSan mode. This includes 2,000 concurrent queue transfers, overflow, unmapped opaque argument values, unexpected threads, heartbeat suspension/resumption, budget exhaustion and initialization failures. These tests do not execute the assembly.
- Actual AArch64 assembly execution and instruction/unwind audit are recorded separately under [abi/](abi/).
- [SDK build result](build-result.json) records the ARM64 binary and source hashes at build time. The later emulator staging attempt failed to load the probe; a successful build is not runtime or physical timing validation.

Run the host checks with `AZ_SDK=/path/to/az-mods-sdk sh tests/run-focused.sh`; run the actual ARM64 fixture with `python3 abi/run-tests.py` using its pinned local Docker image. The normal SDK `azmod-pack build` compiles and validates the probe. It is not in a release or the catalog.

## Gate for a direct menu

This function-entry observer cannot produce a native sequence under the pinned hook policy. The supported SDK `claim_vslot` alternative also rejects this exact slot: `0x2d61c78` is in `.rodata` inside the executable `PT_LOAD` range `0x400000..0x3f5f714` with flags `5` (`PF_R | PF_X`). Pinned `sdk_ep_data_cb` excludes every `PF_X` segment, so `sdk_in_ep_data` returns false and the claim would report `not inside EP147's data` before the patch primitive. This is a verified static/source-policy rejection, not a second runtime claim attempt.

Do not retry `claim_vslot` against this boundary or call the raw vtable primitive from a community mod. If this route is pursued, it needs a separate reviewed core claim-service change with narrowly defined slot authorization, expected-target/ownership checks and exact protection restoration, or a different supported observation boundary. Broadly accepting arbitrary addresses in executable segments would remove an existing SDK restriction. Neither change is implemented here. Any eventual slot observer would only cover calls dispatched through that exact vtable, not direct calls or another table.

After a valid observation boundary exists, a controlled native knob sequence may establish which arguments correspond to direction and which dispatch path reaches Waveform. It cannot establish counter-update ordering, queued-event ownership, click/BACK release behavior or safe handback. No input may be consumed from observation alone.

Independent source review identified two additional schedules a future direct-menu implementation must test: `mixer_browse_knob` samples the old watchdog count before the same frame refreshes it, and `ov_take_menu_handoffs` currently applies pending movement/click before consuming a close request. Test threshold crossing/recovery and simultaneous navigation/click/turn in both orders. Preserve native byte 35 behavior, counter wrap, held releases, modal precedence and SOURCE-row ownership separately.

Private backups, native screenshots, raw logs and runtime scripts stay ignored under `runtime-private/`; generated binaries stay ignored under `out/`. The [runtime note](runtime-evidence.md#selective-cleanup-verified--october-22) retains the refused initialization, blocked original restore and later verified selective cleanup. That cleanup preserved a fresh current baseline rather than restoring obsolete community packages. The emulator was released; a future experiment requires a new verified baseline and explicit ownership.
